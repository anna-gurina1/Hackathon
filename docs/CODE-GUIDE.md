# Как разобраться в Bitwise

Цель этой структуры — чтобы очередную правку можно было найти по её задаче, а не читать весь проект сразу. Код не переписан на другой стек; основные соглашения Flask/Jinja сохранены.

## 1. Начните с одного запроса

Откройте эти файлы по порядку:

1. `run.py` вызывает `create_app()` и запускает сервер при прямом запуске файла.
2. `core/__init__.py` создаёт приложение, подключает базу, CSRF, вход, переводы и blueprints (группы маршрутов).
3. `backend/routes/main.py`: `/explore` принимает запрос каталога.
4. `backend/catalog.py`: `CatalogFilters.from_args()` читает фильтры, `catalog_results()` выбирает поиск компаний или курсов.
5. `database/catalog.py`: строит SQL и возвращает словари карточек без содержимого уроков.
6. `frontend/templates/explore.html` и `partials/macros.html`: превращают данные в HTML.
7. `frontend/static/js/catalog.js`: при наличии JavaScript обновляет результаты без полной перезагрузки. `catalog-cards.js` отвечает только за HTML-элементы карточек.

```text
Браузер GET /explore?q=Python
  → маршрут main.explore
  → CatalogFilters → catalog_results
  → database.catalog → SQLite/PostgreSQL
  → explore.html → готовая страница

При изменении запроса в форме:
  catalog.js → GET /api/search → тот же CatalogFilters/catalog_results
             ← JSON карточек ← тот же database.catalog
  catalog-cards.js → DOM
```

Без JavaScript обычная GET-форма продолжает работать. Не убирайте серверную отрисовку только потому, что есть fetch.

Начальная карточка строится Jinja, обновлённая — JavaScript. Это две реализации разметки с одним форматом данных, а не два разных каталога. При изменении полей карточки проверьте обе. Сведение их в сторонний шаблонизатор добавило бы сложность и зависимости; ради этого рефакторинга оно не нужно.

## 3. Соглашения

- **Маршрут** принимает HTTP, проверяет права, вызывает помощник и возвращает render_template/jsonify/redirect. SQL каталога и разбор фильтров в нём не дублируются.
- **Запрос базы** возвращает данные, но не решает, имеет ли пользователь право быть владельцем компании. Проверка полномочий остаётся в маршруте и `backend/access.py`.
- **Шаблон/renderer** показывает данные. Пользовательские строки должны экранироваться Jinja; JS использует `textContent`, а не `innerHTML`.
- Начальное `_` у Python-функции обозначает внутренний помощник файла. Публичные `search_courses`, `search_companies`, `company_dashboard`, `best_score` сохранены.
- `database/queries.py` переэкспортирует старые имена поиска для совместимости. Новый код лучше импортирует их из `database/catalog.py`.
- Импорт `t()/tn()` в catalog-модулях не нужен: это существующие глобальные функции `main.js`, подключённого раньше. Импорты между самими catalog-модулями — нативные ES modules, сборщик не нужен.

### Почему два режима для неизвестного `by`

HTML-страница прежде возвращалась к Topic, а JSON API возвращал пустой список. Это поведение оставлено явно: `fallback_to_topic=True` используется только страницей. Не меняйте API случайно при изменении формы.

### Почему закрытые курсы встречаются в каталоге

Приватная карточка намеренно видна; доступ к урокам требует записи/подтверждения или приглашения. `status=draft` скрывается. Поиск не должен выдавать тела уроков и видео. Наличие карточки не означает права чтения урока.

### Почему оценка кандидата — не «средняя»

Существующее правило `best_score()` возвращает максимальную попытку любого теста курса, включая неуспешные попытки. Рефакторинг не изменяет его смысл: `_course_scores()` получает то же значение сразу для нескольких учеников и курсов. Новый механизм итоговых оценок — отдельная продуктовая задача.

## 4. Что действительно оптимизировано

Старая загрузка каталога обращалась к связанным урокам каждого курса, хотя карточке нужно лишь число уроков. Теперь SQL считает их, не загружая тексты. Компания присоединяется к запросу заранее.

В кабинете компании раньше для каждого кандидата и каждого завершившего курс повторялись поиск оценки и проверка предложения. Теперь оценки группируются одним запросом, а отправленные предложения собираются в набор пар `(user_id, course_id)`. Связанные записи загружаются пакетно. Для счётчика уроков нужны только ID, не содержимое уроков.

Это уменьшает число запросов, но не означает бесконечную масштабируемость. Пагинация каталога и кандидатов, индексы по планам запросов, кэширование и реальная нагрузочная проверка остаются отдельными задачами. Не добавляйте их наугад без замера на реальных объёмах.

## 5. Почему CSS не объединён в один огромный файл

Порядок подключения: `style.css` → стили страницы (обычно `pages.css`) → `refinements.css`. Последний слой сохраняет доработанный дизайн поверх существующего. В этом обновлении форматирование `refinements.css` развёрнуто в читаемые блоки, порядок правил сохранён.

При правке свойства сначала найдите его через поиск и проверьте каскад. Не создавайте четвёртый файл «final-final.css» и не добавляйте `!important` ради обхода непонятного правила. Полное сведение старых и новых стилей в компонентные файлы требует отдельной визуальной регрессии всех экранов; оно не выполнено автоматически ради меньшего числа строк.

## 6. Тесты — оставить

`tests/` — проверки программы, не задания для учеников. Они не импортируются обычным запуском сайта и не замедляют его страницы.

- `test_permissions.py`, `test_security.py`, `test_workspace_context.py` — права, приватность и контекст компании.
- `test_workspaces.py`, `test_learning.py` — компании и обучение.
- `test_documents.py`, `test_migration.py` — материалы и перенос схемы.
- `test_catalog.py` — серверный каталог, фильтры и экранирование.
- `test_query_refactor.py` — совместимость фильтров/результатов и контроль числа SQL-запросов.
- `test_resilience.py` — некорректные запросы, сбои почты/удаления файлов, сохранение предложений и безопасный возврат в конструктор.
- `test_backup.py` — резервная копия искусственной SQLite-базы, включая кириллицу и пробелы в пути.

Не требуется запускать их при каждом открытии сайта. Запускайте перед передачей изменений команде:

```bash
python -m pytest -q
python translations/check.py
```

Тестовые зависимости отдельно: `requirements-dev.txt`. Для одного запуска сайта достаточно `requirements.txt`. В приложение не добавлены Black/Pyflakes/форматтеры — это инструменты, использованные отдельно при работе, не runtime-зависимости проекта.

## 7. Что не удалять ради чистоты

- `migrations/`: сохраняют историю переходов существующих данных.
- Legacy-поля в `models.py`: могут содержать старые данные и нужны совместимости. Удаление требует миграции и отдельного решения.
- `core/questions.py` и `database/seed.py`: большие файлы могут быть данными/демопримерами, а не плохим кодом. Не удаляйте их только из-за размера.
- `.env.example`: безопасный шаблон настроек, не то же самое, что ваша секретная `.env`.
- `.git/`, база и uploads: это ваши история и данные, а не мусор.

Автокэши `__pycache__`, `.pytest_cache`, `.pyc` не входят в выдаваемый архив и уже исключены из Git. Старые документы не уничтожены: они лежат в `docs/history/` и явно помечены как история.

## 8. Границы внешних сервисов

Сначала сохраняйте результат бизнес-операции, затем отправляйте необязательное уведомление. Сбой письма не должен превращать сохранённое предложение работы в ошибку страницы. Не сообщайте об успешной отправке, если транспорт вернул отказ. Очистка Cloudinary после удаления — best-effort с журналированием: неудача может оставить удалённый файл и требует проверки. Не ослабляйте проверку доступа ради обработки ошибок хранилища.

Терминальные ссылки входа предназначены только для development. В production нужен настроенный почтовый транспорт; отсутствие транспорта не должно печатать тело письма. Тесты используют собственную временную папку uploads и искусственную базу, а не пользовательские данные.
