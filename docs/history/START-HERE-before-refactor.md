# Как запустить и безопасно перенести проект

Если версия с миграцией `0009` уже установлена, для текущей доработки используйте `UPDATE-INSTRUCTIONS.md`: новой схемы базы здесь нет.

## 1. Не заменяйте старую рабочую папку сразу

Распакуйте архив в отдельную папку. Старый проект, его `.env`, базу и Git-репозиторий пока не трогайте. В архиве намеренно нет вашей базы и секретов.

Для пустого тестового запуска выполните команды в README.md.

## 2. Если у вас уже есть SQLite app.db

1. Остановите старый сервер на время пробного переноса.
2. Из новой папки создайте резервную копию, указав путь к СТАРОЙ базе:

```bash
python tools/backup_sqlite.py "ПУТЬ_К_СТАРОМУ_ПРОЕКТУ/app.db" backups
```

3. Убедитесь, что файл копии появился. Скопируйте эту копию в новую папку проекта под именем `app.db`. Исходную базу не перемещайте и не удаляйте.
4. Создайте НОВЫЙ `.env` из `.env.example`. Для пробного переноса `DATABASE_URL` оставьте пустым: приложение будет работать с `app.db` именно в новой папке. Проверьте, что `DATABASE_URL` также не задан в переменных окружения терминала. Не копируйте production DATABASE_URL для локального теста.
5. Если нужно сохранить действительность ранее выданных ссылок и cookies, используйте прежний SECRET_KEY локально; не пересылайте его в чат. При смене ключа старые ссылки и сессии перестанут работать, но сами аккаунты не исчезнут.
6. Выполните:

```bash
python -m flask --app run db current
python -m flask --app run db upgrade
python -m flask --app run db current
```

После обновления должна быть ревизия `0009 (head)`.

7. Запустите `python run.py` и проверьте сценарии ниже. Только после успешной проверки переносите изменения в основной проект.

Если старая база создана без alembic_version, старые миграции умеют подхватить исходные таблицы. Этот конкретный вариант также нужно проверить на копии вашей базы; нельзя гарантировать совместимость с произвольно изменённой схемой.

Если вы уже установили предыдущий архив с ревизией `0008`, не начинайте заново и не удаляйте базу: сделайте бэкап и выполните тот же `python -m flask --app run db upgrade`. Новая ревизия `0009` меняет только политику приватных курсов. Существующие ID, ссылки-приглашения, записи и заявки сохраняются. Ранее выбранные «Скрытые» курсы теперь видны в каталоге — как вы запросили. Их уроки не становятся открытыми.

## 3. Что делает миграция

- Создаёт отдельные компании и членство владельцев.
- Сохраняет старые ID компаний, URL, курсы, записи на обучение, попытки тестов, предложения и заявки.
- Переносит логотип со старого аккаунта компании в компанию. Личное фото теперь отдельное.
- Старые закрытые курсы сохраняет в режиме «по заявке», поскольку раньше они были видимы в каталоге. Миграция `0009` также возвращает приватным курсам из промежуточного архива видимость в каталоге и доступ по заявке или приглашению.
- Старые видео помечает как публичную legacy-доставку `upload`.
- Если у закрытого курса есть старые публичные видео, переводит такой курс в черновик. Прогресс НЕ удаляется. Повторная публикация потребует повторной загрузки видео.
- Не придумывает имя владельца и не объединяет разные почты. Владелец старой компании может заполнить личный профиль в «Редактировать профиль».

Миграции `0008` и `0009` не поддерживают downgrade: несколько компаний нельзя без потерь упаковать в прежнюю модель. Для отката остановите новый сервер, сохраните отдельную копию его текущей базы и восстановите резервную копию вместе со старой версией кода. Изменения после резервной копии при таком откате теряются; для живого проекта нужен план обслуживания.

## 4. PostgreSQL

Не используйте backup_sqlite.py для PostgreSQL. Сделайте резервную копию средствами хостинга или `pg_dump` и проверьте восстановление в отдельную тестовую базу. Миграция содержит PostgreSQL-совместимые операции и сброс последовательности ID, но в этой работе выполнялась на SQLite, не на реальном PostgreSQL.

## 5. Как проверить результат вручную

1. Создайте личный аккаунт и две компании. Выбор в списке сразу открывает кабинет без дополнительной кнопки. В личном кабинете нет авторских прав, даже если человек владелец компании.
2. Создайте черновик в первой компании.
3. Пригласите редактора на другую тестовую почту. До принятия доступа нет.
4. В другом профиле браузера войдите почтой редактора и откройте «Кабинеты и приглашения». Примите приглашение.
5. У владельца откройте «Участники и доступ к курсам» и назначьте редактору курс.
6. У редактора проверьте редактирование назначенного черновика. Другие черновики не должны появляться или открываться по URL.
7. Владелец добавляет урок с текстом и тестом: минимум два ответа, один правильный. Затем публикует.
8. Редактор больше не может изменять курс, в том числе отправкой POST по старому адресу формы.
9. Отзовите доступ к курсу или исключите участника. Его открытая вкладка больше не должна позволять сохранять изменения.
10. В личном кабинете откройте собственный опубликованный курс: нет конструктора и удаления, есть «Начать курс». Пройдите урок и тест. Переключитесь в компанию и обратно: личный прогресс сохраняется. В авторской карточке переход «Пройти как ученик» возвращает к курсу в личном режиме.
11. Проверьте открытый и приватный курс. Приватный виден гостю в каталоге и на странице компании; без доступа уроки закрыты. Заявка требует одобрения, а ссылка-приглашение позволяет записаться напрямую.
12. Перед удалением личного аккаунта сайт потребует отдельно удалить принадлежащие ему компании. Это намеренная защита от случайного удаления всех курсов.

## 6. Почта, видео и AI

Пустой MAIL_SERVER в разработке печатает ссылки в терминал. В production нужен настроенный SMTP или Brevo. Если MAIL_BACKGROUND=1, успешная постановка письма в очередь не гарантирует доставку; смотрите журнал сервера.

Для видео настройте Cloudinary в локальном `.env`. Новые загрузки используют `type=authenticated`; ссылки выдаются авторизованным зрителям на 1 час. Настройку конкретного Cloudinary-аккаунта, проигрывание большого видео и HTTP Range нужно проверить с настоящим сервисом.

**Старые публичные видео остаются доступными по ранее полученным URL, пока вы не удалите/закроете их в Cloudinary.** Повторная загрузка создаёт защищённый ресурс, но не отменяет уже утёкшую публичную ссылку автоматически. После замены приложение пытается удалить старый ресурс. Проверьте удаление и кэш Cloudinary отдельно. Уже скачанное видео отозвать нельзя.

AI-подсказки и перевод остаются необязательными. Ключи в чат не отправляйте.

## 7. Production

- `APP_ENV=production`, собственный SECRET_KEY минимум 32 символа и `PUBLIC_URL=https://ваш-домен` обязательны.
- HTTPS обязателен: production cookies имеют Secure.
- Используйте Gunicorn, не `python run.py`.
- Задайте настройки почты и Cloudinary через секреты хостинга.
- Не выкладывайте `.env`, базы, backups и `.git` в архив для отправки.
- Оплата по-прежнему демонстрационная: переключение тарифа не списывает деньги.
- До открытого запуска нужны нагрузочная проверка, общие лимиты запросов/приглашений и проверка внешних сервисов. Автотесты не заменяют полноценный аудит безопасности.

## 8. Как перенести изменения в Git

Работайте в копии командного репозитория, где нет несохранённых чужих правок:

```bash
git status
git switch -c feature/company-workspaces
```

Ветка — отдельная линия изменений; main остаётся нетронутой. Перенесите исходники из архива, но не удаляйте существующую папку `.git`, свой `.env` и данные. Удаление устаревшего `database/test_queries` также входит в изменения; вместо него есть `tests/`.

После локальных проверок:

```bash
git diff --stat
git status
```

Проверьте, что секреты, базы и backups не попали в список. Затем выберите нужные файлы через Source Control в VS Code, создайте commit (зафиксированную порцию изменений), выполните push (отправку ветки) и откройте pull request для проверки командой. Не делайте force push и не сливайте в main до проверки миграции.
